# Драйвер генератора случайных чисел (Hash-DRBG, модуль `random`)

Источник случайных данных для ядра и пользовательских программ (`/dev/random`, `/dev/urandom`, системный вызов `getrandom`). Криптографическая часть — Hash-DRBG по NIST SP 800-90A на базе SHA-512 из `libxcrypt`. Сам драйвер собирается как отдельный модуль `random.so`, который ядро загружает при старте. Если модуль не загрузился, ядро использует запасной генератор, который не криптографический.

## Расположение

| Файл | Назначение |
|------|------------|
| `src/drivers/random/random_abi.h` | Имена экспортируемых символов и версия ABI |
| `src/drivers/random/random_core.h`, `random_core.c` | Hash-DRBG: инстанцирование, reseed, generate, `hash_df` |
| `src/drivers/random/random.c` | Экспорт в модуль: сбор энтропии, управление состоянием, reseed по счётчику |
| `src/drivers/random/Makefile` | Сборка `bin/modules/random.so` из `random.c`, `random_core.c`, `libxcrypt/src/sha512.c` |
| `src/kernel/random/krandom.c`, `krandom.h` | Фасад ядра: загрузка модуля, выбор реализации, запасной генератор |

## ABI модуля

Модуль экспортирует три символа (`random_abi.h`):

| Символ | Сигнатура | Назначение |
|--------|-----------|------------|
| `purec_random_abi` | `uint32_t (void)` | Версия ABI, сейчас `1` |
| `purec_random_fill` | `int (void *buf, uint32_t n)` | Заполнить буфер случайными байтами, `0` при успехе |
| `purec_random_reseed` | `int (const void *data, uint32_t n)` | Добавить внешние данные в состояние (reseed) |

Ядро получает адреса через `kmod_get` и вызывает их только после проверки всех трёх.

## Жизненный цикл

1. `krandom_init()` (вызывается из `kernel.c:126`) пытается загрузить `/lib/modules/random.elf` через `devman_load_module`. При успехе читаются три символа.
2. При первом вызове `purec_random_fill` или `purec_random_reseed` вызывается `generator_open`. Он собирает 64 байта энтропии и инстанцирует DRBG с персонализационной строкой `PureC-OS purecrypt hash-drbg v1`.
3. Каждые `RESEED_EVERY` (4096) вызовов генерации состояние пополняется свежей энтропией (`hdrbg_reseed`).
4. Запросы больше `PURECRYPT_RANDOM_CHUNK` (256 байт) разбиваются на куски.

## Сбор энтропии (`gather_entropy`)

Для каждого из восьми 64-битных слов:

- берётся `RDRAND` (до 16 попыток), если процессор его поддерживает (`cpuid` лист 1, бит 30 в `ECX`), иначе слово равно нулю;
- измеряется дрожание TSC вокруг цикла из 64 пустых итераций;
- всё добавляется в SHA-512.

Результат — 64-байтовый дайджест. Итоговый буфер получается копированием дайджеста, так как `ENTROPY_BYTES` совпадает с его длиной.

## Запасной генератор ядра (`krandom.c`)

Если модуль не загрузился или его символы не нашлись, `krandom_fill` использует xorshift64* (`fallback_next`). Начальное значение берётся из RDRAND (если есть) XOR TSC XOR константа. Для внешних данных `krandom_mix` подмешивает их в состояние сдвигами.

**Этот генератор не криптографически стойкий.** Его выход можно предсказать, если известно начальное состояние. Использовать его для ключей, паролей и TLS нельзя. Отличить его от модуля можно через `krandom_hardened()`: вернёт `true`, если модуль работает. Ядро пишет это в лог при загрузке (`kernel.c:128`).

## Где используется

- `src/fs/devfs.c:174, 313` — чтение `/dev/random` и `/dev/urandom`, запись в них подмешивает данные (`krandom_mix`).
- `src/kernel/syscall/syscall.c:291` — системный вызов получения случайных байт.
- Сборка: `mk/main.mk:340` (сборка модуля), `mk/main.mk:369` (список модулей для копирования в образ), `mk/main.mk:215` (тест `hdrbg_test`).

## Ограничения

- **Качество энтропии зависит от RDRAND.** Без RDRAND единственным источником остаётся дрожание TSC в 64 пустых итерациях. Это слабый источник, и на некоторых машинах он почти постоянен. Драйвер не проверяет качество собранной энтропии и не делает статистических тестов.
- Значение `HDRBG_RESEED_INTERVAL` (2^48) в коде проверяется, но ядро делает reseed каждые 4096 вызовов, так что до предела дело не дойдёт.
- Путь модуля в `krandom.c` — `/lib/modules/random.elf`, а `Makefile` собирает `random.so`. Переименование при копировании в образ выполняется в `mk/main.mk`. Если образ собран без этого шага, модуль не найдётся и ядро молча уйдёт на запасной генератор. Проверять это нужно по строке `krandom_hardened` в логе.
- Нет блокирующего режима: `/dev/random` ведёт себя так же, как `/dev/urandom`.
- Состояние DRBG глобальное, без привязки к процессу. Параллельные вызовы сериализуются только мьютексом в фасаде ядра.
